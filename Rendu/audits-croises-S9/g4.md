# Audit croisé OpenAPI — Groupe 4 (ThermoSense)

- **Groupe auditeur :** Groupe 1 — Kenza, Enzo, Matteo, Tommy, Valentin
- **Contrat audité :** Groupe 4 — ThermoSense (`ThermoSense_openapi.yaml`, OpenAPI 3.0.3)

## Grille (8 critères)

1. **Endpoint testable sans lire le code — Oui.** `servers` (local/prod/staging), `securitySchemes` Bearer JWT + `security` global, paramètres et bodies en `$ref`, exemples sur les propriétés : on enchaîne `POST /auth/login` (`admin`/`Admin1234!`) puis un appel `/buildings` avec le Bearer, sans toucher au code.
2. **Erreurs 4xx/5xx — Oui.** 400/401/403/404/503 documentées et toutes rattachées à un même schéma `Errors` (`code` machine-readable + `message` + `details[]` par champ). Seul le 500 générique n'est jamais documenté.
3. **Versioning — Partiel.** `info.version: 1.0.0` présent, mais le préfixe `/v1` n'apparaît que dans les `servers` prod/staging — ni en local, ni dans les `paths` — et la stratégie n'est pas explicitée.
4. **Exemples — Oui.** `example` sur quasiment toutes les propriétés (login, `b-001`, coordonnées, timestamps, enums) : suffisant pour bâtir requête et réponse. Réserve : exemples au niveau propriété uniquement, pas de payload complet.
5. **Cohérence des schemas — Partiel.** Très complets et homogènes (`required`, `format`, `enum`, min/max, séparation Request/Response/Patch). Une incohérence : `Sensor.status` n'inclut pas `offline` alors que le contrat documente lui-même un `503 "Capteur hors ligne"` (et `models.ts` définit bien `offline`).
6. **README — Oui.** Stack, prérequis, install, `.env` (`MONGO_URI`/`JWT_SECRET`/`PORT`), `npm run dev`/`build`/`start:prod`, seed avec comptes de test, table des routes, sécurité, tests Bruno : on démarre sans contacter l'équipe.
7. **Cohérence endpoints/ressources — Oui.** Nommage pluriel uniforme, hiérarchie REST claire (`buildings → zones → sensors → measurements` et `actuators → commands`), verbes et codes (201/204) appropriés. Réserve : `POST /users` est taggé `Auth`, et la description annonce des « seuils d'alerte » sans endpoint associé.
8. **Sécurité visible — Oui.** `securitySchemes: bearerAuth` (http/bearer/JWT) + `security` global, avec override explicite `security: []` sur `/health` et `POST /auth/login`. Schéma défini **et** appliqué.

## Synthèse

- **Point fort :** un modèle d'erreur unique et structuré (`Errors` : `code` + `message` + `details[]`) réutilisé sur **toutes** les réponses d'erreur, couplé à une sécurité bien posée (`bearerAuth` global + `security: []` sur les 2 seules routes publiques). Conséquence concrète : un client écrit un seul handler d'erreur et sait d'emblée quelles routes sont ouvertes.
- **Incohérence :** `components.schemas.Sensor.status` = `[active, faulty, maintenance]` ne contient pas `offline`, alors que le contrat documente un `503 "Capteur hors ligne"` (GET sensor / measurements) et que `SensorSchema` (code) a bien `offline`. Un `GET .../sensors` qui liste un capteur hors ligne renvoie donc un `status` hors de l'enum : un client en validation stricte casse.
- **Question :** la description (`info.description`) annonce « Configurer des seuils d'alerte » comme fonction mobile, mais aucun endpoint de seuils n'est documenté, périmètre volontairement hors-contrat, ou oubli de documentation ?
