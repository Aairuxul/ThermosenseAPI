## Grille (8 critères)

1. **Endpoint testable sans lire le code — Oui.** Le contrat suffit : URL, méthode, paramètres typés, auth Bearer.
2. **Erreurs 4xx/5xx — Partiel.** Les codes sont documentés partout, mais le corps d'erreur structuré (`Error`, `RateLimitError`) n'est mis que sur quelques réponses ; la plupart n'ont qu'une description.
3. **Versioning — Oui.** Préfixe `/v1` dans les chemins + registre de versions (`swagger/index.ts`) et dropdown Swagger.
4. **Exemples — Partiel.** Des `example` sur les champs des schémas, mais aucun exemple complet de requête/réponse par endpoint.
5. **Cohérence des schemas — Oui.** `type`, `format`, `required`, `nullable` cohérents. Réserve : `enum` sur `ActuatorCommand.status` mais pas sur `Sensor.status`/`type`.
6. **README — Oui.** Install, Prisma, `npm run dev`, `.env`, liste d'endpoints et exemples curl : on démarre sans contacter l'équipe.
7. **Cohérence endpoints/ressources — Partiel.** Doublons singulier/pluriel (`/sensor` + `/sensors`, `/actuator` + `/actuators`) et `POST /actuators/{id}/commands` qui met à jour l'actionneur au lieu de créer une commande.
8. **Sécurité visible — Oui.** `bearerAuth`, `security` global + routes publiques en `security:[]`, `x-required-roles` sur chaque endpoint.

## Synthèse

- **Point fort :** la sécurité est décrite dans le contrat, pas seulement dans le code — `bearerAuth`, `x-required-roles` sur chaque endpoint, et `POST /sensor/{id}/measurement` documente l'`Idempotency-Key`, la réponse `202` (mode dégradé) et le rate-limit.
- **Incohérence :** le contrat place les routes sous `/v1` (`v1.ts`, `servers: localhost:3000`) mais le serveur les sert sans préfixe (`server.ts` → `/building`). Une requête construite depuis le contrat (`GET /v1/building`) renvoie donc **404**.
- **Question :** pourquoi `LECTEUR` (lecture seule) et `DEVICE_IOT` (mesures) peuvent-ils faire `DELETE /building/{id}` dans `x-required-roles`, alors que votre tableau des rôles dit le contraire ?
